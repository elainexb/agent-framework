# Document governance

This is an isolated candidate, not an installed project or global rule. Its role is to coordinate information ownership and verified changes. Existing project policy owns project-specific requirements; reuse it rather than reproducing it here.

## Establish the requested outcome

Read applicable instructions and the project's existing entry point, then the current task and documents relevant to the request. Use current source files for implementation facts and specifications for intended behavior. Read history only for a required provenance, approval, recovery or unresolved decision.

Follow the user's requested mode: an audit returns findings; a proposal returns a candidate; an authorized edit changes the scoped records. Preserve valid approvals and unsettled decisions. A documentation request does not authorize changing product scope, code, permissions or adopting a global policy.

## Resolve ownership before composing

For each affected topic, locate the existing authoritative section and its real readers or consumers. Use the existing index as the ownership map; do not create a second registry. If ownership cannot be resolved from the materials, report the concrete conflict and pause only the dependent change.

Classify the proposed information by its next use:

- Integrate new or changed requirements, reasons, exceptions and durable decisions into their existing owner.
- Point navigation, AGENTS and other entry points to an existing policy, stating when to read it. Keep genuinely unique instructions at their chosen owner; do not turn a pointer into a second copy of the policy.
- Query inexpensive implementation facts from code, configuration, schema or existing commands. Preserve intended requirements even when the code currently violates them.
- Retain history only for a distinct evidence, decision, approval, license or recovery purpose. Carry still-valid information into current owners before retiring its old reading path.
- Omit proposed content with no concrete later use. When the user explicitly requires an artifact, preserve that request and explain any necessary ownership or portability distinction.

Create another document only when a distinct reader, lifecycle, reusable purpose or evidence identity justifies it. File count is not a success criterion. Record necessary findings in the existing task or review record; do not generate a new report for every application.

## Prepare and integrate the change

Identify the affected current statements, references and task state before editing. Read their latest contents and necessary sources. Integrate changes in the owned sections, replacing superseded assertions and preserving unrelated information and other writers' changes. Update affected references in the same scoped change; keep original historical evidence intact.

Repeated execution should find the remaining difference rather than append the same change again. After interruption, inspect what actually survives. If the baseline has changed, reconcile or report the conflict before overwriting it. A multi-file operation is not atomic merely because an individual file replacement is atomic.

## Verify before downstream use

Check the candidate against the user's goal and actual materials, not against this Skill alone:

| Check | Evidence to inspect |
|---|---|
| Ownership and necessity | Every changed fact has an identifiable current owner and later use; another current document does not independently maintain its meaning. Navigation remains a pointer. |
| Preservation and structure | Effective constraints, exceptions and unique information survive; the owned fields contain the change; superseded statements are removed; unrelated sections and history remain intact. |
| Sources and current scope | Relevant sources were actually read; implementation facts and intended requirements remain distinct; changed dependencies invalidate affected old verification rather than merely receiving a new date. |
| Mechanical validity | Applicable existing checks for index membership, links, anchors, source identity and historical integrity actually ran, with their documented limitations. |
| Readiness and actual effects | Required checks match the current candidate and inputs; missing, FAIL or UNKNOWN results are disclosed before dependent use. Requested mode and authority match the observed edits or proposed text. |

Use existing mechanical tools only for the claims they support. Review semantic ownership, preservation and necessity against real sources; neither a successful exit nor a matching hash proves them. Reuse the same evidence across applicable Skills rather than running duplicate checks.

If an actual change-acceptance interface exists, use it and inspect its real result. Otherwise report that enforcement is not connected; this instruction is not an implementation of a mandatory gate. Do not make an absent, unrequested gate a reason to block an otherwise verifiable ordinary edit, or claim universal prevention from a cooperative self-check.

Preserve failures and distinguish generated, applied, verified, installed and user-accepted outcomes. Store the applicable checks and evidence with the existing task. Give each check PASS, FAIL, UNKNOWN or N/A and its scope; unexecuted tests remain NOT_RUN. On failure, correct only within authorized scope and recheck affected claims; do not retry without a bound or weaken the expected outcome until it passes.

Completion means the requested scoped result is inspectable, required checks have actual evidence, and unresolved limits are explicit. It does not mean all possible future inputs, sessions or writing paths have been proven safe.
